Introduction
Lizeral Engine is a solo-developed, lightweight modern 3D game engine. Built entirely from scratch on the Vulkan API, it sheds traditional graphics legacy baggage to deeply align with modern GPU rendering pipelines—fully embracing Bindless Architecture, Mesh Shaders, and Hardware Ray Tracing.

At its core, the engine is powered by a pure data-driven ECS (Entity-Component-System) architecture, coupled with a custom-built Qt visual editor driven by C++ static reflection. It is dedicated to exploring the ultimate performance and highly decoupled workflows of modern game engine development.

Design Philosophy: The Geek's "Scalpel"
If today's commercial behemoths (like Unreal Engine 5 or Unity) are all-encompassing "Swiss Army knives," the philosophy behind Lizeral Engine is to forge a sharp, transparent, and laser-focused "scalpel".

Unburdened by the heavy legacy compatibility of giant engines, Lizeral Engine chooses to travel light, making absolutely zero compromises in embracing the most cutting-edge graphics paradigms. We don't chase bloated, "all-in-one" features; instead, we explore a singular possibility: that on a solo-developer scale, one can still elegantly harness the most advanced low-level technologies—dynamic Ray-Traced Global Illumination, Spatiotemporal Denoising (SVGF), and GPU-driven spatial acceleration—encapsulating them within a transparent, elegantly architected digital foundation.

It is not just a creative tool, but a hardcore tribute to, and reconstruction of, the low-level art of modern AAA engines.

Core Foundation: Pure Data-Driven ECS ArchitectureIn Lizeral Engine, we have completely discarded the bloated GameObject inheritance trees found in traditional game engines (like early Unity or classic C++ engines), fully embracing Data-Oriented Design (DOD). The ECS (Entity-Component-System) architecture is not merely the skeleton of the engine; it is the lifeblood that keeps rendering, physics, and gameplay logic running at blistering speeds.
  1. Paradigm Shift: The Core Philosophy of ECSUnder traditional OOP (Object-Oriented Programming) architectures, game objects are often a tangled mix of logic and data, leading to severe memory fragmentation and massive CPU Cache Misses during iteration. Lizeral Engine's ECS strictly adheres to a rigorous principle: "Absolute isolation of data and behavior."Entity: No longer a monolithic class, but merely a lightweight uint32_t integer ID. It acts simply as a "conceptual tag" that stitches various components together.Composition over Inheritance: A Maserati with headlights is no longer class Car : public Vehicle. Instead, it is simply Entity ID = 42, dynamically outfitted with Mesh + Transform + RigidBody + PointLight components.

  2. Component DesignIn Lizeral, components are exceptionally pure POD (Plain Old Data) structures. They contain absolutely no virtual functions and zero business logic—only contiguous data fields.This design brings two massive advantages:Memory Contiguity: Components of the same type are tightly packed into arrays in memory, allowing the CPU to leverage SIMD and prefetching mechanisms for blazing-fast batch processing.Extreme Serialization Friendliness: Paired with C++ static reflection, we can directly dump a block of memory into JSON, achieving ultra-low-cost scene saving and loading.

  3. Registry ImplementationThe Registry is the central database of the engine. It manages the lifecycles of all Entities and the memory pools of all Components.Sparse Set Mapping: Under the hood, the Registry utilizes Sparse Set data structures. This not only guarantees dense storage of component data but also achieves $O(1)$ complexity for component addition, removal, and lookup.View Queries: When processing logic, there is no need to traverse a scene tree. A System simply requests a View from the Registry: "Give me all entities that possess both a Transform and a PointLight." The Registry instantly returns perfectly aligned data pointers for the System to iterate through at maximum speed.

Deep Dive I: Zero-Coupling Rigid Body Physics SystemWhile traditional physics systems are often deeply entangled with game objects, in Lizeral, the physics engine (based on Bullet Physics) achieves perfect decoupling and two-way synchronization with the ECS.Operating as a stateless "processor," the Physics System's logic is exceptionally elegant:Data Subscription: The system requests a View containing <TransformComponent, RigidBodyComponent> from the Registry.State Initialization (One-Way): Upon detecting an entity newly outfitted with a RigidBodyComponent, the system reads its Transform position and rotation, converts it into a Bullet btRigidBody, pushes it into the physics world, and caches the pointer back into the component.Physics Tick: During each frame's EngineTick, the system calls Bullet's stepSimulation for pure mathematical crunching. At this moment, physics calculations run wild in an isolated memory space, completely undisturbed by external logic.Data Write-Back (Two-Way Sync): Once the simulation steps, the System iterates through the View again, extracts the latest physical coordinates from Bullet's btTransform, and overwrites them back into the ECS's TransformComponent.Architectural Advantage: Throughout this entire process, the Physics System has no concept of what a "Maserati" or a "desk" is; it only sees batches of rigid body data subjected to forces. This profound isolation not only paves the way for multi-threaded physics stepping but also allows developers to instantly add or strip away a RigidBodyComponent with a single click in the editor, achieving true "hot-swappable" physics states.

Deep Dive II: Extremely Elegant Camera Roaming SystemA camera controller is the ultimate litmus test for ECS decoupling. Lizeral Engine dismantles the traditionally monolithic Camera class into three orthogonal components, demonstrating immense reusability.In our architecture, a free-roaming 3D camera is born from the "chemical reaction" of the following parts:TransformComponent: Solely responsible for spatial position $(X,Y,Z)$ and rotation $(Pitch, Yaw, Roll)$.CameraComponent: Strictly handles optical properties (FOV, Near/Far Plane) and matrix generation (ViewMatrix, ProjectionMatrix).CameraControlComponent: Exclusively stores interaction parameters (movement speed m_speed, mouse sensitivity m_sensitivity).The Flow of the Camera Control System:Every frame, the CameraControlSystem intercepts keyboard (W/A/S/D) and mouse inputs. It then queries the Registry for all entities possessing the three aforementioned components.Calculate Displacement: Computes the delta vector based on the CameraControlComponent's speed parameters and key inputs.Update Spatial State: Applies the delta to the TransformComponent.Derive Optical Matrices: Extracts the updated Transform coordinates, combines them with the CameraComponent's FOV to recalculate the ViewProj matrix, and packs it into the global BDA data block for GPU consumption.Architectural Advantage (The Magic Moment):Because the logic relies entirely on component composition, "roaming control" is no longer an exclusive privilege of the camera! If, within the editor, you strip the CameraControlComponent from the camera entity and attach it to an entity equipped with a DirectionalLightComponent (the sun)—you can instantly use W/A/S/D and your mouse to pilot the angle and position of the sun itself! This level of freedom, shattering conventional inheritance hierarchies, is exactly the mesmerizing technical charm of Lizeral Engine's ECS architecture.
